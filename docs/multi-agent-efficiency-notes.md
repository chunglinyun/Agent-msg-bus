# 多 agent 對話效率：想法記錄

狀態：**討論記錄，尚未成案**。從 frontend 討論中分出來的一半（另一半見 frontend 相關計畫）。

## 現況瓶頸（由貴到便宜）

1. **沒有共享上下文**。A 跟 B 的對話 C 看不到，於是 C 只能再問一次「現在進度如何」。每次補問都是一輪完整的 send → recv → 回覆，是目前最貴的浪費。
2. **`@all` 是 O(N²)**。廣播一句話，N 個成員各回一句，而這些回覆又各自廣播給所有人。爆炸量主要來自禮貌性 ack，不是實質內容。
3. **輪詢成本**。每次 `recv --wait 540` 佔一次 Bash call。但 recv 本來就一次 splice 整個佇列，已是批次，優先度低。

## 對應解法

### A. `msg log -n 20`（優先做）

broker 保留最近 N 筆（暫定 200）訊息的 ring buffer，新增指令讓成員自行讀取近期 bus 對話，取代「跟人問進度」。

- 投報率最高：換掉大量往返，成本約 10 行。
- **與 frontend 共用同一塊 buffer**：frontend 的 tap 需要它來補歷史，兩個功能一次到位。因此順序上先做 ring buffer + tap，`msg log` 與 frontend 都掛在其上。

### B. 溝通守則（零程式碼）

`msg-bus-skill/SKILL.md` 與 `AGENTS-template.md` 各加三條：

1. 非點名不回（`@all` 的內容若與自己無關，不必回應）。
2. 不要 ack（「收到」「好的」不送）。
3. 只送結論，不轉播過程。

`@all` 的 O(N²) 主要由 1、2 造成，用提示詞就能壓掉，不需要協定改動。

### C. `msg ask @name "..." --wait 300`（低優先）

send + 阻塞等對方下一則訊息，只動 `msg.js`，不動協定。但 `askpeer.js` 已覆蓋單問單答場景，先不做。

## 明確不做

thread／topic 分流、優先級佇列、訊息 ID 與相關性追蹤、持久化 DB。等 bus 上同時有 5 個以上 agent 且實測會亂才重新評估。
