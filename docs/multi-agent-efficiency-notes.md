# 多 agent 對話效率：想法記錄

狀態：**B（五條守則）與 C（一行 send && recv）已於 2026-08-23 寫進 `msg-bus-skill/SKILL.md` §2 與
`AGENTS-template.md`；A 續延後**。從 frontend 討論中分出來的一半——frontend 那一半已經做完（`docs/web-frontend-*.md`）。
取用面（buffer 怎麼讀）已拆到 `docs/bus-context-retrieval-plan.md`。
落地時一併移除了 SKILL.md 舊的 `One message, one point`——它鼓勵拆訊息，與守則 3 直接牴觸。

**優先順序照成本走：零程式碼的先做——C 的一行與五條守則同屬一次 `SKILL.md`／`AGENTS-template.md` 的修改 → A 續延後。**
本文有兩組編號（瓶頸 N 與守則 N），引用時一律寫明是哪一組。

## 現況瓶頸（由貴到便宜）

1. **來回次數**。一次 send → recv → 回覆，貴的不是 body 而是**那一輪**：每個模型回合都要把 system prompt、skill、對話歷史、工具定義整包重送，一兩萬 token 起跳。所以一次多餘的澄清往返，成本等於整則訊息重寫幾十次。主要來源是沒有共享上下文——A 跟 B 的對話 C 看不到，於是 C 只能再問一次「現在進度如何」。
2. **`@all` 是 O(N²)**。廣播一句話，N 個成員各回一句，而這些回覆又各自廣播給所有人。爆炸量主要來自禮貌性 ack，不是實質內容。
3. **內容是寫給人看的**。每則訊息都當作有人在讀而寫成散文，寫的一方付一次、讀的每一方再各付一次。每則都在繳，但相對於一整輪來回，省下來的是尾數——**先修 1，再修 3**。
4. **輪詢成本**。一次空回的 timeout 跟一次真的來回一樣貴（貴的是回合本身），但 `msg-bus-skill/SKILL.md` 的監聽迴圈已有「兩次空回就停」封頂，而 wait 540 貼著 Bash 的 600 秒上限，沒得再省。

## 對應解法

### A. `msg log -n 20`（**已延後，整段移到 `docs/bus-context-retrieval-plan.md`**）

> 前置的 ring buffer + tap 已隨 frontend 完成（`broker.js:81`），所以 A 本身只剩十行。
> 但 200 筆未經篩選的原始訊息塞進 agent 的 context 是浪費且容易造成幻覺，因此**先不實作**；
> 等訊息可以被精準挑選（description）或先被摘要之後再回頭評估。**而且守則先做完，A 會自己變小**：
> body 只剩一行加一個路徑時，200 筆就不再是昂貴的貼上。

### B. 五條守則（零程式碼，原九條）

落地時是 `msg-bus-skill/SKILL.md` 與 `AGENTS-template.md` 裡的**同一份清單**，不是兩份。

**主張：bus 傳指標與決策，檔案承載內容。** bus 上的 agent → agent 是控制通道——誰在做什麼、決定了什麼、產出在哪裡。它只需要對收方的模型無歧義，**不需要人讀得懂**。人要讀的東西有兩個，而且都已經存在：

- `docs/` 底下完整的 plan／spec 文件（版本控管、可以照自己的節奏讀）；
- 最後回覆給 user 的內容。

```
✗  "我完成了 auth refactor，以下是我改了什麼與為什麼……"（400 字）
✓  "done: auth refactor → docs/auth-refactor-plan.md §3"
```

**成本結構決定守則的優先順序**（見瓶頸 1）：少一次來回 ≫ 少一則訊息 ≫ 訊息更短。

還有一個結構性的免費午餐：**約定放在 system prompt 裡每個 session 只付一次，而且會被 prompt cache 命中；訊息裡的每個字都是新 token。** 這是唯一邊際成本為零的壓縮方式，也是這一整組守則能成立的原因。

五條守則：

1. **非點名不回，不 ack。** `@all` 的內容若與自己無關就不回應；「收到」「好的」不送。
   `@all` 的 O(N²)（瓶頸 2）主要由這一條壓掉，用提示詞就能解決，不需要協定改動。
2. **只送結論與路徑。** 長內容進檔案、訊息只給路徑（含章節），不把檔案內容貼進 bus，不轉播過程。
   這不只是短，是**延後**：對方不需要就永遠不付那筆錢。
3. **一次問完、一次答完。** 問題附上對方回答所需的全部前提；回答附上對方接著要用的全部結果。
   **寧可長，不要多一輪**——與其餘四條牴觸時一律以這條為準。這是唯一直接打瓶頸 1 的一條；
   把訊息壓短卻換來一次澄清往返是淨虧損。
4. **寫給收方的模型，不寫給人。** 不寒暄、不複述雙方都已知的上下文、不為了排版加 markdown 裝飾。
5. **例外：意外與決策要連理由一起傳。** 判準要可執行——**如果對方接下來的動作會因為這件事而不同，就要講。**
   `done: X` 說不出「順手改了 schema」，而那正是最該傳的那部分。

**不要再加回「差量更新」（只送上次之後變了什麼）。** 它的前提是「同一個對象、而且它還記得上一則」，
而這個前提會被本專案自己的功能打破：對方 `/compact` 過、或它是後來才 join 的，差量就靜默地不完整，雙方都不會發現。

**接受的代價：人在 frontend 的即時可讀性會下降。** 真正的風險不是不好看，是**人發現不了 agent 走偏**——
那正是 `/stop` 存在的理由。所以人的介入點要跟著換：看 `docs/` 的 plan／spec、看 `thinking` 指示燈知道誰在忙、
用 session 指令介入，而不是逐則讀懂 bus。

**怎麼知道有效：數來回，不是數字數。** 主指標是**完成同一件事所需的 send/recv 次數**——
瓶頸 1 說 body 是尾數，照 body 長度優化反而會鼓勵違反守則 3 的行為。

### C. 一問一答併成一個 tool call（**最高優先，零程式碼**）

一問一答現在是 `send` 一個 Bash call、`recv --wait` 再一個，**每個 tool call 就是一次模型回合**，
所以至少兩輪。併成同一個 Bash call 就直接省一輪，正好打在瓶頸 1——而這不需要新指令：

```bash
node <dir>/msg.js send @b --as a "q" && node <dir>/msg.js recv --as a --wait 300
```

`msg ask @name "..." --wait 300` 只是這一行的糖，唯一多給的是可發現性。先把這一行寫進 `SKILL.md`，
跑一陣子、確認 agent 真的會用，再決定要不要包成指令。

**已知天花板（不論用哪個形式都在）**：`recv` 是從**自己的佇列**整批 splice（`msg.js:107`），
跟剛才送出去的那個問題沒有任何關聯。三個以上 agent 在線時，回來的可能是 @c 的訊息而不是 @b 的回答，
而且會靜默錯配。這正是「明確不做」裡的訊息 ID 與相關性追蹤，不打算為它建協定。
兩個 agent 的場景沒問題；`SKILL.md` 寫這一行時要附一句「回傳的是下一則到達的訊息，不保證來自對方」。

## 明確不做

thread／topic 分流、優先級佇列、訊息 ID 與相關性追蹤、持久化 DB。等 bus 上同時有 5 個以上 agent 且實測會亂才重新評估。
C 的錯配（見上）是這個決定的已知代價，用提示詞裡的一句話標示，不用協定解。
